# Architecture decision records

One file per decision. Status is one of proposed, accepted, superseded.

| ADR | Decision |
|-----|----------|
| [0001](0001-preview-host.md) | Superseded by 0011. Preview host is the target repository's own Vite, driven through its JS API with a generated config |
| [0002](0002-source-mapping.md) | Superseded by 0015. Element to source mapping through a pre-transform JSX stamp plus React fiber walking |
| [0003](0003-edits.md) | Superseded by 0015. Edits are surgical AST edits on TSX followed by the target's formatter |
| [0004](0004-acp.md) | ACP is the only agent interface, wrapped in `packages/acp`; launch configurations are data |
| [0005](0005-effect.md) | Superseded by 0009. Effect Schema on the wire, plain TypeScript services |
| [0006](0006-designs-package.md) | Superseded by 0011. Screens live in a workspace package inside the target repository |
| [0007](0007-catalogue.md) | (The catalogue: amended by 0040 and 0042, a view over the component files.) Component catalogue from the TypeScript 5 compiler API plus `cva` parsing |
| [0008](0008-checkpoints.md) | (Storage and revert: amended by 0039.) Agent turn checkpoints are snapshots of the designs directory |
| [0009](0009-effect-runtime.md) | Effect 4 runtime, `RpcGroup` over WebSocket, SDK-backed `AcpAgent` service |
| [0010](0010-storage-modes.md) | Settings and state in one of three storage modes: the desktop's home, a configuration file in the repository, or nothing saved |
| [0011](0011-preview-split.md) | (Iframes: superseded by 0034. One host: amended by 0037. The editor entry: amended by 0039. The framework split: amended by 0042, the frame's interface is preview-core's.) Storybook's separation: editor, framework-neutral preview core, renderer, framework package; screens resolve from an anchor package instead of being one |
| [0012](0012-spaces-pages-router.md) | Screens become pages of a space (a canvas since 0019), routed by their file path, with the editor holding the router state in its own URL |
| [0013](0013-agent-scope.md) | Agents are confined to the repository by an operating system sandbox around their process, the same for every ACP agent |
| [0014](0014-editor-mcp.md) | The editor answers agents over MCP: what the project is and where they are working, not a second way to edit files |
| [0015](0015-design-documents.md) | Pages are design documents (`.page.json`) the tool owns; the design system is imported by an agent; an agent turns a page into code |
| [0016](0016-figma-import.md) | A Figma file is read by rules into pages; which component is which is an agent's decision, or the user's, asked in the thread |
| [0017](0017-a-command-in-the-repository.md) | The tool is a command run in the repository, served to the browser; the desktop shell is removed (it returns with 0031) and a checkout is tried on a project as a linked devDependency |
| [0018](0018-agents-work-on-the-canvas.md) | Three selection colours (element, component, agent); chats found by a picture of their scope; a Vibe toolbar of design-system values; agents' work drawn on the elements; nodes linked by reference |
| [0019](0019-canvases.md) | (Snapshots' storage: amended by 0037.) Spaces become canvases, listed above the pages as Figma lists a file's pages; canvases and pages are copied, with or without an agent; variants are built; assets are shared; snapshots are named points in history |
| [0020](0020-pages-have-optional-urls.md) | A page is named by its file and serves an optional URL kept in `canvas.json`; the Pages panel is the prototype's, and canvases are switched from under the project |
| [0021](0021-links-name-pages.md) | A link names a page file (or a URL, back, another site) and follows the page through renames and URL changes; links are set from the element; the prototype shows its hotspots |
| [0022](0022-mcp-2026-and-asking-the-user.md) | The editor speaks MCP 2026-07-28; the tools' definitions an agent carries are halved; `ask_user` waits for the answers within the turn, on a card any MCP server's form is drawn as |
| [0023](0023-design-system-setup.md) | (Component notes: amended by 0042.) A design system is set up in five steps (inventory, define, map, migrate, verify) the user sees, stops and redoes; each step is a pair of snapshots of the working tree, in the tool's own snapshot store since 2026-10-26 (no git needed) |
| [0024](0024-style-systems.md) | (Class writer: amended by 0038.) Tokens are read and written by a style system adapter beside the framework (Tailwind v4 today), in a neutral model the server speaks; the preview draws every token as a custom property |
| [0025](0025-design-system-sync.md) | (Values: superseded by 0028. Foreign token names: amended by 0039. Component drift: retired by 0042.) One Sync works out the case (scratch, code, Figma, Figma onto code, keep in sync) and lays out the steps; token values live in the code; Figma's tokens are matched to the code's (rules, an agent with the user) and compared against a committed baseline; the configuration file is `ultrapaint.config.json` |
| [0026](0026-pages-one-node-per-line-and-pngs.md) | Pages are JSON written a node per line; with `pagePngs`, every page is drawn as a PNG beside its file, redrawn only when what it was drawn from changes |
| [0027](0027-design-md.md) | `DESIGN.md` follows the open format at the repository root; the code keeps the values and the front matter mirrors them both ways, with the document's tokens matched and compared against a baseline as Figma's are |
| [0028](0028-the-design-holds-the-values.md) | (Tokens file: amended by 0035.) The design holds every token's value; the code, Figma and DESIGN.md are sides compared with it against baselines; the code follows on export (or at once with `codeTokens: auto`); the preview draws the design's values; `design.tokens.json` is the Design Tokens export |
| [0029](0029-component-specs.md) | (Linking a spec read off the code: amended by 0038. Specs read off cva: superseded by 0040. Specs and drafts: replaced by 0041's components.) A component's behaviour is its code's and its look can be the design's: specs in `specs/`, drawn over the real component by `data-ed-c`/`data-ed-v` and `data-slot`, read off cva classes, drafts for components the code does not have yet |
| [0030](0030-the-implementation-link.md) | Pages and specs are linked to the files that implement them, with a status and the design as implemented; `/implement` sends what changed; behaviour notes; page states; design and implement threads; the MCP `handoff` tool |
| [0031](0031-the-desktop-app.md) | (Built-in agents: amended by 0038.) A desktop app is an Electron shell around the same server and web build; git is not needed and writing to it is a setting, off by default; the tool keeps its own snapshot store; a run file and `--ready-json` say where a server runs; `Platform` has the shell's hooks; a new design from nothing is `ultrapaint new`, which the app's New design dialog runs |
| [0032](0032-floating-cards-one-canvas-workspace.md) | (Key handlers: amended by 0037.) Vibe and Design are one canvas workspace, each side panel put away on its own; the panels, the rail and the tools are cards floating over the canvas; every command is in one list, which the ⌘K palette and the shortcut sheet read; on a Mac the desktop window's buttons sit in the title card |
| [0033](0033-the-canvas-keeps-its-previews.md) | (Iframe pool and process: superseded by 0034.) The previews run in a process of their own; the camera moves the canvas without React; a frame's preview is parked loaded while the frame is away and moved back with `moveBefore`; new previews load three at a time; Layers draws only the rows on screen; `pnpm bench:canvas` measures it |
| [0034](0034-frames-in-the-editors-page.md) | (The frame's host: amended by 0039. The repository's components: superseded by 0040.) The repository's components run in the editor's page, loaded once through the server's `/preview/`: every frame (the canvas, the prototype, the pictures) is a shadow root with one stylesheet for all, the preview core called directly; no iframes, one port over SSH |
| [0035](0035-design-tokens-hold-the-values.md) | `design.tokens.json` holds every token's value and `design-system.json` the rest; another tool's change to the tokens file is the design's value, with no Sync step; the `designTokens` baseline and the `dtcg` source go |
| [0036](0036-responsive-views.md) | A page is drawn in views of any width beside its frame; a node's fields can differ from a design system breakpoint on (`at`), mobile-first; an edit lands at the breakpoint of the view it is made in; each frame draws the tree resolved at its width, a component's `matchMedia` answers for its frame, and the code has Tailwind's prefixes |
| [0037](0037-deep-modules.md) | Each concept that was written in several places has one module: the token table, a token's value, the design system's files, the Sync engine and its sides, the snapshot store, the agent launcher, a thread's session and its cards, typed tasks, provenance, the page runtime, the preview's turn and kernel, the editor's frames, the shell bridge, the location, key bindings, node edits, menu actions |
| [0038](0038-deep-modules-second-review.md) | What 0037 left half-done has one module too: the composition root and a project test layer, the settings in force, flows in their services, the design system's sides, the canvas layout, the spacing scale and lengths, a node's style as declarations, a built-in agent as one descriptor, the server's data in the web, the selection, a thread's view, showing a left panel, Layers' tree |
| [0039](0039-deep-modules-third-review.md) | (The frame's host: amended by 0042, one writer.) What a third review found has one module too: the editor's tools named for the agent, checkpoints in the snapshot store, Tailwind's utilities, the token with a value, a node's fields, the frame's host, the preview server's config, the editor entry |
| [0040](0040-the-editors-own-primitives.md) | (The primitives are 0041's system components. An instance's layout: amended by 0042, the catalogue's.) The canvas draws the editor's own primitives on Base UI, not the repository's components: their slots filled by children that name them, their look the design's, each frame a viewport for their popups; nothing of the repository's runs, so the preview server and the sandbox go; `/implement` applies a primitive to the application's own component |
| [0041](0041-system-and-app-components.md) | (Changing an app component and the migration: amended by 0042.) Everything placed is a component, of two origins: system components (the editor's own on Base UI, 0040's primitives) and app components (the project's own); one `components/<Name>.component.json` each, replacing specs and drafts; a system component's look gains layout per part, content when empty, optional parts left out and item templates, its behavioural parts fixed; an app component has properties, slots, variants kept in `at` and nesting, and is edited in place; Sync migrates what came before in one step |
| [0042](0042-deep-modules-fourth-review.md) | What the system components left written in several places has one module too: the catalogue over the component files, an instance's slots (filling them and their layout), the design's look set once per preview, a component file's codec with property changes made on the server, the migration, replacing a node in place, the frame's interface in preview-core; the catalogue's service, the frame's layout reports, component notes, the framework service and two unused settings go |
